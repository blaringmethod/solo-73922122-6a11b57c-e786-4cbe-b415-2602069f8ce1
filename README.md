# 复扫页数核对页

古籍复扫验收用的网页工具：导入「批次修订清单」与「页数汇总单」，勾选待验
批次后，只在**整单组合**严格覆盖所选批次时给出总页数；组合之间总页数不同
则列出分歧的两组单号与合计；没有有效组合则明确提示无法出数。

## 规则如何落地

- **整单计入**：一张汇总单要么整张采用，要么整张不用；不接受按批次拆分。
- **恰好一次**：每个所选批次在组合中恰好出现一次，且组合中不能含任何未选
  批次（多出来的批次会让整张单失去资格）。
- **有效组合**：只有「所含批次修订号全部等于现行修订号」的单才可参与组合；
  含未知批次、单内重复批次的单在导入时即拒绝。
- **报数**：所有有效组合总页数一致 → 报该数；不一致 → 报分歧，给出最小和
  最大两组（单号 + 各自合计），不报单一数字；无有效组合 → 无法出数。
- **同一次已提交状态**：每次导入或更版都追加一个不可变快照（`submissions`
  行 + 该提交号下的批次/汇总单行）。核对在一个 SQLite 读事务里按同一个
  提交号取清单与汇总单，杜绝跨状态混读。更版时汇总单原样复制进新快照，仍
  记录旧修订号，于是自动变为「不采用」。
- **以勾选时所见的提交为准**：核对表单带隐藏字段 `from`，记录勾选时页面显示
  的提交号；服务端只按该提交号取清单、单据状态与核对结论，不再默认取「当前
  最新提交」。过期判定覆盖三种情况：
  - 另一窗口整套重导（即使批次号、修订号、页数完全相同）→ 过期，要求重新
    勾选，绝不用新单据给旧页面报数；
  - 任一**所选**批次的修订号在勾选后被改过（逐提交比对历史链，`r2 → r3 → r2`
    也算改过）→ 过期；
  - 缺少 `from` 的旧链接或 `from` 指向不存在的提交 → 提示重新勾选。
  只改动了**未勾选**批次的更版不使勾选过期，此时仍在旧提交上核对，页面同时
  标明「核对所用提交」和「最新提交」。
- **计算期间不放松**：核对结论算出后、以及页面渲染完成后各再校验一次提交
  历史；若这期间生效的提交使勾选过期，本次不输出任何结论（连结果区块都不
  渲染），提示刷新后重新勾选。只有未勾选批次被改版时才保留结论并更新最新
  提交的显示。
- **上限**：最多 16 个批次、40 张汇总单；解析层、仓储层与 SQLite 触发器三处
  都做了限制。

## 运行

### Docker Compose（交付方式）

```bash
docker compose up --build
# 打开 http://127.0.0.1:8000
```

数据落在命名卷 `collation-data` 的 `/data/collation.sqlite3`，容器以非 root
用户运行，带健康检查。

### 本机直接跑

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
DATABASE_PATH=./data/collation.sqlite3 gunicorn --bind 127.0.0.1:8000 wsgi:app
```

### 测试

```bash
pip install -r requirements-dev.txt
python -m pytest
```

### 联机演示

服务启动后：

```bash
python3 demo/demo.py http://127.0.0.1:8000 demo/out
```

脚本只走 HTTP，按以下顺序演示（每步自判通过/未达预期，末行给出总结论）：
初始导入 → 核对 B01+B02 得 150 页 → **另一窗口用相同批次号和修订号重导**，
旧链接必须拒绝出数并提示重新勾选 → 从新提交重新勾选得 150 页 → 把 B01 改到
r3 再改回 r2，旧勾选仍须过期 → 只改未勾选的 B03 时旧勾选仍可核对 → 缺少
`from` 的旧链接须拒绝 → 重新导入并制造同覆盖不同合计的分歧。
记录写入 `demo/out/transcript.md`，关键响应 HTML 也一并保存。

## 输入格式

批次清单，每行一个批次：

```
B01 r2
B02, rev3
B03 修订=1
```

汇总单用**空行**分隔；每张首行是 `单号 总页数`，其后每行 `批次 修订号`：

```
S1 150
B01 r2
B02 r2

S2 90
B03 r1
B04 r1
```

`#` 开头的整行是注释。汇总单若没有空行分隔，第二张的「单号 页数」会被当
成上一张的批次行；导入前的交叉校验会以「批次清单中不存在」报错拦截，不会
静默错并。

## 验证结果（据实）

- `python -m pytest`：**53 项全部通过**（解析、仓储、并发、Web 流程，以及
  600 组随机用例与暴力枚举的差分测试）。新增 13 项覆盖本次修复：同内容重导
  失效、所选批次改版后改回原值仍失效、仅未勾选批次改版仍可核对、缺 `from`
  旧链接、计算中/渲染中提交导致过期不出结论、结论链接可复现、表单回传所见
  提交号。
- 额外离线差分：5000 组随机实例上，位掩码 DP 与暴力枚举在状态、组合数、
  总页数、分歧极值上**完全一致**（0 不符）。
- 16 批次 / 40 张单边界：单次核对约 0.3–0.5 秒。
- 4 worker × 4 线程 gunicorn 下重复导入与核对结果一致；同一基准提交上的两
  个并发更版只有一个成功、另一个被拒（见 `tests/test_concurrency.py`）。
- 用**生产依赖**（`requirements.txt`：Flask 3.1.3 + gunicorn 23.0.0）实跑
  gunicorn 并完整跑通 `demo/demo.py`。
- 已修正的实现问题：`wsgi.py` 相对导入导致 gunicorn 启动失败；单行紧凑汇总
  单格式有歧义，已改为强制空行分隔并在文档说明；DP 原保留「任意两个总数」
  导致分歧示例不一定是极值，已改为每状态保留最小/最大见证。
- 已修正的核对页缺陷：核对表单原来只带批次勾选，服务端按「当前最新提交」取
  快照，旧页面提交后会拿新单据报数。现由表单携带勾选提交号 `from`，按该提交
  取数并逐提交校验历史链；重导或所选批次改版（含改回原值）都提示重新勾选；
  只改未勾选批次时在旧提交上继续核对；计算与渲染期间提交生效且使勾选过期时
  本次不出结论。页面明确标注核对所用提交，清单、单据状态与结论同源。
- 实测：`gunicorn 23.0.0 --workers 4 --threads 4` 下跑通新版 `demo/demo.py`
  （`demo/out/transcript.md` 全部步骤「通过」），包含相同内容重导后旧链接
  拒绝报数、改回原值仍拒绝、未勾选更版仍报 150 页、缺 `from` 拒绝、最后从
  最新提交复测报出 T1/T3 分歧（150/170）。

### 未能在本环境验证

本机没有 Docker 守护进程/容器运行时（`docker` 命令不存在），也没有可用的
rootless 命名空间（`unshare -Ur` 被拒），因此 `docker compose up --build`
**未实际执行**。`Dockerfile` 与
`docker-compose.yml` 已按可构建方式写好；等价的启动命令（同一 `wsgi:app`、
同样的 `DATABASE_PATH`、gunicorn 多 worker）已在本地以固定版本依赖跑通。
请在具备 Docker 的机器上补跑一次 `docker compose up --build` 确认镜像层。

## 剩余事项

- 无鉴权、无审计人字段；页面面向内网验收台，若需多人使用应加登录与操作人。
  因此任何拿到 `from` 与勾选参数的人都能复现同一次结论；`from` 不是权限凭证。
- 核对链接里的 `from` 只标识提交，不防篡改；数据库是唯一的提交真相。若需防
  手工改参数，可在 `from` 上附 HMAC 签名（当前内网场景未做）。
- 只支持手工粘贴/表单导入，未接扫描系统导出文件；格式若要扩展需同步改
  `app/parsing.py`。
- 提交历史只展示最近 8 条，未提供“回滚到某次提交”的入口（数据已保留，可
  后续加只读回看）。
- 超大汇总单（接近 40 张、每张覆盖大量批次）时采用 2^16 状态 DP；当前上限
  下性能已测，但若上限提高需重新评估。
- 过期判定按提交链逐条比对，历史很长时每次核对都要读一遍后续提交的批次行
  （实测 200 条后续提交约 22 ms，可接受）；若提交量级大幅增长，可在
  `submissions` 上缓存基线的批次指纹。
